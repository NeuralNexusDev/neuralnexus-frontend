# Test plan: permissions

## admin_permissions.go

| ID | Function | Scenario Type | Scenario | Precondition | Expected Result | Priority | Notes |
|----|----------|---------------|----------|---------------|------------------|----------|-------|
| PM-01 | `adminPermissionsListHandler` | Happy Path | The list route renders every permission the API returns | Fake API answers `GET /permissions` with two permissions (`{"id":"1","node":"pets.read","description":"Read pets","value_type":"","merge":""}` and `{"id":"2","node":"pets.max","description":"Max pets","value_type":"int","merge":"max"}`); `GET /admin/permissions/list` with `HX-Request: true` through `NewWebServer("", false).Setup()` | Status 200, `Content-Type` `text/html; charset=utf-8`, body holds both nodes, both descriptions, the row ids `permission-1` and `permission-2` and the create form id `admin-permission-create-form`, and has no `autofocus` attribute; the API saw exactly one call, `GET /permissions` with no body | P1 | Tests do not use `t.Parallel`. The package needs `NN_API_URL` and `NN_SITE_URL` exported at init. The `Content-Type` comes from `renderAll` in page.go |
| PM-02 | `adminPermissionsListHandler` | Edge Case | An empty permission list renders the empty state and the create form | Fake API answers `GET /permissions` with `[]` | Status 200, body holds the id `admin-permissions-empty` and `admin-permission-create-form` and holds no `permission-` row id | P1 | |
| PM-03 | `adminPermissionsListHandler` | Error Path | An API failure answers with its status and message and no list | Fake API answers `GET /permissions` with 403 and detail `"Missing permission"`, then 500 and detail `"database down"`, then 500 with no detail | Status 403, 500, 500; body is exactly `Missing permission`, `database down` and `Failed to load permissions`; `HX-Retarget` is `#page-error` and `HX-Reswap` is `innerHTML` in every case | P1 | Table-driven over the three answers. The headers and the body layout come from `failFragment` in page.go. The last case checks the fallback message `loadPermissions` passes |
| PM-04 | `adminPermissionsListHandler` | Error Path | A 401 from the API sends the browser to the login page | Fake API answers `GET /permissions` with 401 | Status 401, `HX-Redirect` `/login`, empty body | P1 | Outcome comes from `failFragment` in page.go |
| PM-05 | `loadPermissions` | Happy Path | The permissions decode into the data and focusList is passed through | Fake API answers `GET /permissions` with the two permissions from PM-01; called directly with `apiSession{r: testutil.NewRequest()}` and focusList `false`, then `true` | Error nil; `Permissions` equals the two decoded permissions in API order, with `Merge` `"max"` and `ValueType` `"int"` on the second; `FocusList` equals the argument; the API saw one call, `GET /permissions` | P1 | Table-driven over the two focusList values |
| PM-06 | `loadPermissions` | Edge Case | An empty array gives an empty list and no error | Fake API answers `GET /permissions` with `[]` | Error nil and `len(Permissions)` is 0 | P2 | |
| PM-07 | `loadPermissions` | Error Path | An API failure returns an error and an empty data value | Fake API answers `GET /permissions` with 500 and detail `"database down"`, then with 401 | First is `*apiError` with Status 500, Message `database down`, Method `GET` and Path `/permissions`; second `== errUnauthorized`; the returned data equals the zero `AdminPermissionsData` in both | P1 | Table-driven over the two answers |
| PM-08 | `adminPermissionCreateHandler` | Happy Path | A create without a value type posts only node and description, then reloads and renders the list and a fresh form | Fake API answers `POST /permissions` with 201 and `{"id":"9","node":"pets.write","description":"Write pets","value_type":"","merge":""}` and `GET /permissions` with a list that holds that permission; `POST /admin/permissions` with `HX-Request: true`, form `node=pets.write`, `description=Write pets`, `value_type=` and `merge=max` | API saw `POST /permissions` with body exactly `{"description":"Write pets","node":"pets.write"}` and `Content-Type` `application/json`, then `GET /permissions`, and nothing else; status 200; body holds `permission-9`, `pets.write`, `admin-permissions-list` and `admin-permission-create-form` | P0 | The form always posts `merge`, so it is present here and must not reach the API. The body string is exact because `json.Marshal` sorts map keys. Status and content type come from `renderAll` in page.go |
| PM-09 | `adminPermissionCreateHandler` | Edge Case | Node and description are trimmed before they are sent | Form `node=  pets.write\t` and `description=\n Write pets  ` | API saw body exactly `{"description":"Write pets","node":"pets.write"}` | P0 | |
| PM-10 | `adminPermissionCreateHandler` | Happy Path | An int permission sends its value type and merge rule | Form `value_type=int`, `merge=max`, then `merge=min` | API saw body exactly `{"description":"Max pets","merge":"max","node":"pets.max","value_type":"int"}` and the same with `min` | P0 | Table-driven over the two merge values |
| PM-11 | `adminPermissionCreateHandler` | Edge Case | An int permission without a merge field sends an empty merge | Form `value_type=int` and no `merge` field | API saw body with `"merge":""` and `"value_type":"int"`, and the handler does not choose a default | P0 | |
| PM-12 | `adminPermissionCreateHandler` | Edge Case | A non-int value type sends no merge even when the form carries one | Form `value_type=string` with `merge=max`, then `value_type=string_list` with `merge=min` | API saw a body with the `value_type` key set to the form value and no `merge` key | P0 | Table-driven over the two value types |
| PM-13 | `adminPermissionCreateHandler` | Edge Case | A blank node is forwarded to the API and the API's refusal is shown | Form `node=   ` and no description; fake API answers `POST /permissions` with 400 and detail `"Node is required"` | API saw body exactly `{"description":"","node":""}`; status 400; body holds `Node is required`; no `GET /permissions` call | P0 | The handler has no check of its own, so the API decides what a valid node is |
| PM-14 | `adminPermissionCreateHandler` | Error Path | A 400, 409 or 422 refusal shows the message and restores the node field with the submitted text | Form `node= Bad Node `; fake API answers `POST /permissions` with each of 400, 409 and 422 and detail `"Node is invalid"` | Same status as answered; `HX-Retarget` `#page-error`; body holds `Node is invalid`, the id `admin-permission-create-node` and the untrimmed text ` Bad Node ` as the field value; the API saw only the POST | P0 | Table-driven over the three statuses. The status switch is in `fieldRefusal` in page.go and the headers in `failFragment`. The value is the raw form value, not the trimmed one that was sent |
| PM-15 | `adminPermissionCreateHandler` | Error Path | Any other API failure shows only the message and restores nothing | Fake API answers `POST /permissions` with 403 and detail `"Missing permission"`, then 500 with no detail | Status 403, then 500; body is exactly `Missing permission`, then `Failed to create the permission`; the API saw only the POST | P0 | Table-driven over the two answers. The last case checks the fallback message |
| PM-16 | `adminPermissionCreateHandler` | Error Path | A 401 on the create sends the browser to the login page | Fake API answers `POST /permissions` with 401 | Status 401, `HX-Redirect` `/login`, empty body, and the API saw only the POST | P1 | Outcome comes from `failFragment` in page.go |
| PM-17 | `adminPermissionCreateHandler` | Error Path | A failed reload after a successful create reports it and appends the created row and a fresh form | Fake API answers `POST /permissions` with 201 and the permission from PM-08, and `GET /permissions` with 500 and detail `"database down"`, then with 500 and no detail | Status 500 in both; body holds `The change was made, but the page could not be refreshed: database down` (then `...: Failed to load permissions`), the id `permission-9`, `pets.write` and `admin-permission-create-form`; the API saw `POST` then `GET` | P1 | Table-driven over the two reload answers. The message prefix comes from `afterWrite` in page.go. The row and form come from `AdminPermissionAdded` and `AdminPermissionForm` |
| PM-18 | `adminPermissionCreateHandler` | Error Path | A 401 on the reload after a successful create sends the browser to the login page | Fake API answers `POST /permissions` with 201 and `GET /permissions` with 401 | Status 401, `HX-Redirect` `/login`, empty body | P1 | `afterWrite` in page.go returns the 401 unchanged |
| PM-19 | `adminPermissionDeleteHandler` | Happy Path | A delete sends an empty DELETE, then reloads and renders the list with focus on it | Fake API answers `DELETE /permissions/7` with 204 and `GET /permissions` with a list that no longer holds permission 7; `DELETE /admin/permissions/7` with `HX-Request: true` | API saw `DELETE /permissions/7` with an empty body and no `Content-Type`, then `GET /permissions`, and nothing else; status 200; body holds `admin-permissions-list` and the heading `admin-permissions-title` with the `autofocus` attribute, and holds no `permission-7` | P0 | `focusList` true moves focus to the list heading once the delete button has gone |
| PM-20 | `adminPermissionDeleteHandler` | Edge Case | The permission ID is path-escaped when it is sent to the API | Fake API answers each escaped route with 204 and `GET /permissions` with `[]`; requests `DELETE /admin/permissions/a%20b`, `/a%2Fb`, `/a%3Fb` and `/a%23b` | API saw the DELETE with URI `/permissions/a%20b`, `/permissions/a%2Fb`, `/permissions/a%3Fb` and `/permissions/a%23b` in turn, each as a single path segment | P0 | Table-driven over the four IDs. The router unescapes the ID in `r.PathValue` and the handler escapes it again |
| PM-21 | `adminPermissionDeleteHandler` | Error Path | An API refusal shows its message, keeps the list and does not reload | Fake API answers `DELETE /permissions/7` with 404 and detail `"Permission not found"`, then 409 and detail `"Permission is in use"`, then 500 with no detail | Status 404, 409 and 500; body is exactly `Permission not found`, `Permission is in use` and `Failed to delete the permission`; `HX-Retarget` `#page-error`; the API saw only the DELETE | P0 | Table-driven over the three answers. A second admin deleting the same permission first gets the 404 case |
| PM-22 | `adminPermissionDeleteHandler` | Error Path | A 401 on the delete sends the browser to the login page | Fake API answers `DELETE /permissions/7` with 401 | Status 401, `HX-Redirect` `/login`, empty body, and the API saw only the DELETE | P1 | Outcome comes from `failFragment` in page.go |
| PM-23 | `adminPermissionDeleteHandler` | Error Path | A failed reload after a successful delete reports it and removes the deleted row | Fake API answers `DELETE /permissions/7` with 204 and `GET /permissions` with 500 and detail `"database down"` | Status 500; body holds `The change was made, but the page could not be refreshed: database down` and the directive that deletes the element `permission-7` (`delete:#permission-7`); the API saw `DELETE` then `GET` | P1 | The message prefix comes from `afterWrite` and the directive from `rowGone`, both in page.go |
| PM-24 | `adminPermissionDeleteHandler` | Edge Case | A failed reload after a successful delete with a non-numeric ID reports it without a row directive | Same as PM-23 with `DELETE /admin/permissions/abc` | Status 500; body is exactly `The change was made, but the page could not be refreshed: database down` | P2 | `rowGone` in page.go returns nothing for an ID that is not all digits |
| PM-25 | `adminPermissionDeleteHandler` | Error Path | A 401 on the reload after a successful delete sends the browser to the login page | Fake API answers `DELETE /permissions/7` with 204 and `GET /permissions` with 401 | Status 401, `HX-Redirect` `/login`, empty body | P1 | `afterWrite` in page.go returns the 401 unchanged |
